# Vigil.

[![CI](https://github.com/kartik6049/vigil-core/actions/workflows/ci.yml/badge.svg)](https://github.com/kartik6049/vigil-core/actions/workflows/ci.yml)

**Built by Kartik Sahani.**

A fraud-monitoring core for payments: a PostgreSQL schema, a Node + Express + TypeScript API with a rules engine and a pluggable ML scorer, a live event stream, an analyst case queue with safe concurrent claiming and an append-only audit log, and a web console.

> **All data is synthetic.** Accounts, names, cities, merchants and transactions are generated by `db/seed.ts` and `simulator/simulate.py`. No real people, banks or payment data are involved, and the "fraud" is injected patterns, not real fraud.

**Live demo:** https://kartik6049.github.io/vigil-core/ · sign in as `analyst@demo` or `admin@demo`, password `demo1234`. The API runs on a free tier that sleeps when idle, so the first sign-in can take about 30 seconds.

## What it does

1. A transaction arrives at `POST /transactions` (service key). The API stores it idempotently on `external_ref`.
2. A scorer returns a risk score and per-feature reasons. Without `ML_SCORE_URL` a built-in stub scorer is used; with it, the API calls that service with an 800 ms timeout and carries on if it is down.
3. The rules engine evaluates four configurable rules (velocity, new city, amount spike, dormant account) against the account's history.
4. A transaction is flagged if the model says high risk, **or** any rule fires, **or** the sender account is already blocked. A case opens, priority 1 when model and rules agree.
5. Analysts claim cases (no two get the same one), write a note, and block or clear. Blocking also blocks the sending account.
6. Everything that changes state writes an audit row in the same database transaction.

## Architecture

```
simulator (GitHub Actions cron)         web console (GitHub Pages, no build step)
        │  POST /transactions                    │  REST + SSE (fetch streaming, Bearer token)
        ▼                                        ▼
   ┌─────────────────────  API (Express + TypeScript)  ─────────────────────┐
   │ zod validation · JWT auth · rate-limited login · helmet · CORS allowlist│
   │ ingest → scorer (stub or HTTP, 800 ms) → rules engine → case + audit    │
   └───────────────┬───────────────────────────────────────────┬────────────┘
                   │ raw parameterised SQL (pg)                │ optional
                   ▼                                           ▼
            PostgreSQL 16                              ML scoring service
   (roles, indexes, materialized view,                 (Phase 2, not in this repo)
    append-only audit trigger)
```

## Run it locally

You need Node 22+ and either Docker or any Postgres 16.

```bash
cp .env.example .env          # then set JWT_SECRET and SERVICE_KEY to long random strings
npm install
npm run db:up                 # Docker Compose Postgres (skip if you use your own / Neon)
npm run db:setup              # migrate, apply grants, seed demo users, accounts and rules
npm run dev                   # API on http://localhost:3000
npm run web                   # console on http://localhost:8080  (second terminal)
```

Feed it traffic:

```bash
pip3 install -r simulator/requirements.txt
set -a; source .env; set +a      # loads SERVICE_KEY from your .env
API_URL=http://localhost:3000 python3 simulator/simulate.py --count 60

# or a steady stream for testing: 20 per minute until 1,000 have been sent
API_URL=http://localhost:3000 python3 simulator/simulate.py --total 1000 --count 20 --interval 60
```

Tests use a separate database (`vigil_test`, created by the Docker setup). The test setup refuses any database whose name does not contain "test". To also run the check that the restricted role cannot modify the audit log, pass its URL:

```bash
TEST_APP_DATABASE_URL=postgres://vigil_app:vigil_app@localhost:5432/vigil_test npm test
```

The map on the Geography page needs an India boundary file; see `web/data/README.md`. Without it the page still works on a plain frame.

## Design decisions worth explaining

**Two database roles.** The owner role runs migrations, grants and seed. The API connects as `vigil_app`, which can read and write the working tables but only `SELECT` and `INSERT` on `audit_log`. A trigger also rejects `UPDATE` and `DELETE` on `audit_log` for everyone, including the owner, so the log is append-only even if the application is compromised or has a bug.

**Claiming a case is race-free.** `POST /cases/next` picks the next case with `FOR UPDATE SKIP LOCKED` and assigns it in the same statement, so two analysts clicking at once get different cases and never block each other. Claiming or resolving a specific case takes `SELECT ... FOR UPDATE`. The concurrency tests fire parallel requests at the same case and assert that exactly one wins.

**Optimistic locking on resolve.** Every case has a `version`. `resolve` must send the version the analyst last saw. If the case changed (someone else resolved it, it was reassigned), the API answers `409` and changes nothing; the console reloads. Version, then status, then assignee are checked inside the locked transaction, and the case update, transaction update, account block and audit rows commit together or not at all.

**Idempotent ingest.** The sender's `external_ref` is unique. A repeat returns `200` with `duplicate: true` instead of creating a second transaction or case, so retries are safe.

**Explainability is stored, not recomputed.** Each transaction keeps its `reasons`: model contributions (`source: model`), rule hits (`source: rule`) and system notes such as `model_unavailable` or `account_blocked`. The case page renders exactly what the decision was based on.

**Cursor pagination.** Lists use opaque keyset cursors with tuple comparison. Cursors carry the timestamp as Postgres text (microseconds). A JavaScript `Date` only holds milliseconds and would skip rows that share a millisecond.

**Money is never a float.** `numeric(14,2)` in the database, decimal strings in JSON.

**Dashboard reads are cheap.** Hourly charts read a materialized view refreshed every five minutes through a `SECURITY DEFINER` function (the API role is not the view owner, and gets no extra privileges).

### JWT trade-off

The console keeps the 1-hour access token in memory and in `sessionStorage` so a refresh does not sign you out. Any script running on the page (an XSS bug) could read it. An `httpOnly` cookie would hide the token from scripts but needs CSRF protection and a same-site deployment, which does not fit a static site on one domain calling an API on another. Mitigations here: every interpolated value in the console is HTML-escaped by default, tokens expire in an hour, the algorithm is pinned to HS256, helmet sets security headers, and the stream is read with `fetch` so the token never appears in a URL. The reasoning is also written in `web/js/session.js`.

### SSE assumes one API instance

The event hub is in memory. Running two instances would split the stream. To scale out, publish through Postgres `LISTEN/NOTIFY` or Redis.

## Measured query performance

Run by `db/explain/run.sh`, which builds a scratch database, drops the index or view, measures, restores it, measures again, and prints the table. These numbers came from that script on a small cloud VM, so treat the ratios as the point, not the milliseconds.

Measured on PostgreSQL 16.15, 2 vCPU, 1,000,000 synthetic transactions, 30,442 cases (300 live). Median of 7 warm runs of `EXPLAIN (ANALYZE, BUFFERS)`, execution time only.

| Query | Before | After | Change |
|---|---|---|---|
| Velocity rule, one account, 10-minute window | 0.103 ms | 0.072 ms | 1.4x |
| Account history, last 20 transactions | 0.440 ms | 0.195 ms | 2.3x |
| Case queue (50 live cases, priority then age) | 2.768 ms | 0.060 ms | 46.1x |
| 7-day hourly chart | 155.927 ms | 0.187 ms | 833.8x |

What this shows, honestly:

- The **partial index** `cases_queue_idx` indexes only open and in-review cases, so the queue stays fast as the resolved history grows. Without it Postgres sorts the live set each time.
- The **materialized view** turns a 7-day scan and aggregate into reading about 170 rows.
- The two `transactions` rows improve only modestly. The velocity window is 10 minutes, and `transactions_created_at_idx` already narrows that to a handful of rows, so the per-account index adds little *here*. It earns its place for wide windows (the `amount_spike` rule looks back 30 days) and for the history list, and the gap grows with table size and per-account volume. I kept the row to show the result as measured rather than choose a flattering query.

Plans and raw output: `db/explain/results.md`.

## Deployment (all free tiers)

| Piece | Where | Notes |
|---|---|---|
| Postgres | [Neon](https://neon.com/pricing) | 1 GB and 100 compute-hours a month on the free plan. Use the owner URL for migrations and the nightly reset, the `vigil_app` URL for the API. |
| API | [Render](https://render.com/docs/free) web service | Free instances sleep after about 15 minutes idle and take about a minute to wake; the console shows a "waking the demo server" message. |
| Console | GitHub Pages | `pages.yml` deploys `web/` and writes the API URL into `web/config.js`. |

**1. Database.** In Neon, create the `vigil_app` role (`create role vigil_app login password '...'`), then run the setup against the direct (non-pooled) owner URL:

```bash
read -s "DATABASE_URL?Neon OWNER url: "; export DATABASE_URL; echo   # zsh; in bash use: read -s -p ... DATABASE_URL
npm run db:setup
unset DATABASE_URL
```

**2. API on Render.** Root directory blank, build `npm ci --include=dev && npm run build`, start `npm start`, health check path `/health`. Environment:

| Name | Value |
|---|---|
| `NODE_VERSION` | `22` |
| `APP_DATABASE_URL` | Neon URL for the `vigil_app` role |
| `JWT_SECRET` | long random string (`openssl rand -hex 32`) |
| `SERVICE_KEY` | long random string, different from your local one |
| `CORS_ORIGIN` | the origin of the console, e.g. `https://kartik6049.github.io` (no path) |
| `TRUST_PROXY` | `1` (the API sits behind Render's proxy) |

**3. Console.** Set the repository variable `API_BASE_URL` to the Render URL, set Pages to deploy from GitHub Actions, then run the `pages` workflow.

**4. Traffic and reset.** Add the repository secrets `API_URL` and `SERVICE_KEY` (simulator) and `DATABASE_URL` (owner connection, nightly reset).

Workflows: `ci.yml` (lint, typecheck, tests against Postgres 16), `pages.yml`, `simulate.yml` (a small synthetic batch every 30 minutes; delayed fraud labels are carried between runs in the Actions cache), `reset-demo.yml` (nightly wipe and reseed).

## API

Full contract in `openapi.yaml`. Highlights: `POST /auth/login`, `POST /transactions` (service key), `GET /transactions`, `GET /cases`, `POST /cases/next`, `POST /cases/{id}/claim`, `POST /cases/{id}/resolve`, `GET /stream` (SSE: `txn.new`, `txn.flagged`, `case.updated`), `GET /stats/*`, `GET`/`PATCH /rules` and `GET /audit` (admin).

## Ideas for improvement

- Replace the stub scorer with a real model behind `ML_SCORE_URL` (Phase 2), publish daily precision, recall and drift to `model_metrics_daily`.
- Push notifications for priority-1 cases (the `Notifier` hook exists and is a no-op).
- Fan out SSE through Postgres `LISTEN/NOTIFY` for multiple instances.
- Refresh tokens in an `httpOnly` cookie if the console and API move to one domain.
- Partition `transactions` by month once it passes tens of millions of rows.
